# Axial 0.16.0: raw effects only where you allow them

Name a file in its project entry, and only that file may read the clock, open files, start processes or construct an
`HttpClient`. Every other file is held to the service, so tests stay deterministic and no one slips a
`DateTime.Now` into domain code.

```xml
<Compile Include="LiveClock.fs" AxialCapability="clock" />
```

**Your own APIs get the same protection.** A payments gateway, a message bus, a vendor SDK: describe it in a small
`.capability.toml` file and ship that file in your package. Every project that references the package gets the same
guardrail, and findings that name your service, the environment field, an example call and the test fake.

```toml
name = "payments"
service = "IPayments"
replaces = [ "ctor:Acme.Gateway.GatewayClient" ]
fake = "TestPayments()"
```

**Reviews show only what lets more code through.** `axial policy review` opens with the changes that need a human.
Any raw-effect exception comes first, to be read one by one. Renames, moves and anything that only tightens the policy
pass without approval.

**Exceptions stay rare and explained.** When Axial can't do something yet, one call may carry a comment that names the
missing feature or says why the call is deliberate:

```fsharp
// axial-allow-raw-effect: (why: this test checks the real clock)
let now = DateTime.UtcNow
```

**Raw tasks and threads follow the same rules.** A file whose job is raw concurrency, such as an OS bridge, claims
`concurrency`; one deliberate `Task.Run` or `TaskCompletionSource` elsewhere carries a `(why: …)` comment. Blocking
waits on monitors, events, semaphores and threads are now reported like `.Result` and `.Wait()`.

**Permissions expire when they stop mattering.** An exception comment that no longer allows anything, and a claim on a
file that no longer makes the raw call, are both reported.

Also in this release:
- Rules have names. A finding reads `warning AXG001: raw-effect: …`, and allowances, notes and the toml name the rule:
  `// axial-allow-raw-effect: …`, `[exemptions] raw-concurrency = […]`.
- Full Guardrails checks are faster, and the analyzer CLI ships precompiled for linux-x64 and win-x64.
- `orDie`, `retryForever`, `Deferred.poll` and `Deferred.make` fit into any workflow without `widenError`.
- `Cache.getSure` reads caches that cannot fail.
- Packages that use Reified now depend on Reified 0.14.0.

## Guardrails

Capabilities:

- **Built in.** `clock`, `random`, `guid`, `timezone`, `blocking`, `processors`, `environment`, `concurrency`,
  `console`, `filesystem`, `process`, `http` and `websocket`. `axial capabilities [--json]` lists them with the files that claim
  each one.
- **Your own.** A `<name>.capability.toml` file with `name`, `service` and `replaces`, plus optional `env`, `field`,
  `example`, `live`, `fake`, `level` and `guardrail`, named by an `<AxialCapabilityDefinition Include="…" />` item. A
  malformed definition, an unknown key, a duplicate name, or an API another capability already covers fails the build
  with the reason.
- **Claims.** `AxialCapability="name[;name]"` on a `Compile` item. A claimed file may call only the APIs it claims; any
  other raw call in it is reported, with a note saying which capability the file claims. Claiming an undefined
  capability fails the build. A `host` file may still make raw calls without a claim.
- **Allowances.** `// axial-allow-raw-effect: reason (gap: name)` or `// axial-allow-raw-effect: (why: reason)` allows one
  call, on its line or the next. stale-allow reports an allowance that names neither, a file-wide raw-effect allowance, and an
  allowance that allows nothing because a claim, a `host` role or a `forbid` level already decides the call. A claim on
  a file that makes no raw call for that capability is an stale-allow warning.
- **Raw concurrency (raw-concurrency).** A file that claims `concurrency` may construct tasks, threads and
  `TaskCompletionSource`s and start work with `Task.Run`; dropped-work (discarded work) and task-surface (raw `Task` surfaces) do
  not apply to it either. Elsewhere, one call may carry `// axial-allow-raw-concurrency: (why: reason)` or `(gap: name)`,
  with the same rules and review as an raw-effect allowance. The `capabilities` role no longer exempts raw concurrency.
- **Blocking coordination.** `Monitor.Wait`, `WaitHandle.WaitOne`/`WaitAll`/`WaitAny`/`SignalAndWait`,
  `ManualResetEventSlim.Wait`, `SemaphoreSlim.Wait`, `Thread.Join`, `CountdownEvent.Wait` and
  `Barrier.SignalAndWait` are raw-effect `blocking` waits, with Flow replacements in the advice. `lock`, `Monitor.Enter`,
  `Interlocked` and `Volatile` stay unreported.
- **Advice.** A finding names the service, the environment field, the interface, an example call and the test fake.
  For a platform service it says that no environment change is needed and how tests control it. An effect that no
  capability covers offers a definition to write, with the match filled in.
- **Counts.** `axial check` shows how many raw calls each project was allowed: in claimed files (per capability), by
  allowances (per gap, plus a count of whys), and in host files (`--json`: `allowedEffects`).

Policy review:

- The lock records each capability definition and each project's claimed files.
- Needs approval: a definition or `replaces` entry removed, `enforce` lowered to `guide`, a project claiming a
  capability for more files, and every new suppression.
- Passes on its own: a new definition or `replaces` entry, `guide` raised to `enforce`, a claim removed, or a claimed
  file renamed or moved. Claims are compared by count per project, so moving a claim to another file in the same
  project also passes.
- The output opens with a count of what needs approval and the next step. Groups follow in reading order, each with a
  line on what it lets through: effect allowances first, then capabilities, rule levels, roles and the rest. Claims
  show as a table per project, and removals collapse to one count line per group.
- The build's drift warning and `axial policy review`, which gates releases, use the same comparison.

Speed:

- Full mode converts each file's typed tree once and shares it across rules. Effect rules are looked up by type,
  suppression comments are read once per file, and the analyzer CLI runs without dynamic PGO. On Axial's core library
  the Guardrails step of a Full build takes about 10.8 seconds, down from 12.9.
- Release packages carry the analyzer CLI precompiled (ReadyToRun) for linux-x64 and win-x64, which makes Full checks
  about 12 percent faster there. The package grows from about 24 MB to 67 MB. Other platforms, and a runtime major
  version that does not match, use the portable copy.

## Flow

- `Flow.orDie`, `Flow.retryForever` and `Deferred.poll` return a free error type, so they bind in any workflow without
  `widenError`.
- `Deferred.make` takes the creating flow's error as a fourth type parameter, for the same reason.
- `Cache.getSure` reads a cache whose loader cannot fail (`Cache<'key, Never, 'value>`) in any workflow.

## Fixes

- Axial, Axial.HttpClient, Axial.Process and Axial.Hosting.GenHttp work in `dotnet fsi` from Debug builds. Their
  `task` blocks disposed resources through `TaskBuilderBase.Using`, which the FSharp.Core in `dotnet fsi` lacks; they
  now dispose with `try/finally`.
- The policy lock records only allowances in ordinary `//` comments, as the analyzer reads them. An allowance quoted in
  a string, an XML doc or a block comment is no longer listed as a new exception; `axial policy review` shows those
  entries as removed, which needs no approval.

## Breaking changes and migration

| Was | Now |
| --- | --- |
| A `capabilities`-role project could make any raw call | a file makes a capability's raw calls only when its `Compile` item claims it. A role whose `effects.ambient` is `allow` still allows every raw call in it |
| `[boundaries]` in `Axial.Guardrails.toml` | an error that says what to do instead; delete the section |
| `[runtime].files` in `Axial.Guardrails.toml` | an error that says what to do instead; each listed file claims `concurrency` on its `Compile` item |
| The `capabilities` role exempted raw tasks and threads (AXG009) | a file claims `concurrency`, or one call carries `// axial-allow-raw-concurrency: (why: reason)` |
| AXG009 could not be allowed by a comment | `// axial-allow-raw-concurrency: (why: reason)` or `(gap: name)` allows one call |
| `Monitor.Wait`, wait handles, `ManualResetEventSlim.Wait`, `SemaphoreSlim.Wait`, `Thread.Join`, `CountdownEvent.Wait`, `Barrier.SignalAndWait` were not reported | raw-effect (AXG001) `blocking` findings: claim `blocking`, or use the Flow replacement the finding names |
| `// axial-allow-AXG001: reason` in a boundary file | claim the capability on the file; otherwise end the allowance with `(gap: name)` or `(why: reason)` |
| `// axial-allow-file-AXG001: reason` | claim the capability on the file's `Compile` item |
| `// axial-allow-AXG003: reason`, `// axial-note AXG014: reason` | the rule's name: `// axial-allow-raise-in-flow: reason`, `// axial-note task-surface: reason`. stale-allow (AXG002) reports each old comment with the name to use |
| `[exemptions] AXG009 = […]` | `[exemptions] raw-concurrency = […]`; the old key fails the build with the name to use |
| `Category` metadata on `AxialGuardrailRule` | ignored; remove it. A rule that a service owns belongs in a capability definition |
| Suppressions for AXG003–AXG008 only in boundary files | in any file; each is still a review item |
| `Deferred.make<'env, 'error, 'value> ()` | `Deferred.make<'env, 'error, 'value, 'workflowError> ()`; type inference usually fills the last parameter |
| `orDie` and `retryForever` returned `Flow<'env, Never, 'value>` | a free error type; drop the `Flow.widenError` that followed them |

To migrate a repository:

1. Run a Full build. Every raw call in a file that is not `host` and claims nothing is now reported.
2. For each file that implements a service, or tests one against the real thing, add `AxialCapability="<name>"` to its
   `Compile` item. `axial capabilities` lists the names. A file compiled into two projects is claimed in each.
3. Remove `axial-allow-raw-effect` comments from claimed and `host` files; stale-allow points them out. Rewrite any other call
   to use the service, or keep the allowance and end it with `(gap: <name>)` or `(why: <reason>)`. In test projects a
   raw call is only a warning, so an old allowance there can simply go.
4. Delete `[boundaries]` and `[runtime]` from `Axial.Guardrails.toml`; the build fails until you do. Each file that
   `[runtime]` listed, and each raw-concurrency file in a `capabilities`-role project, claims `concurrency` instead,
   or better, moves to Flow concurrency. If the toml sets
   `"effects.ambient" = "allow"` on any role but `host`, remove that too: it still exempts the whole role, so claims
   would decide nothing there.
5. Rename rules from numbers to names in comments and the toml: `axial-allow-AXG001` becomes `axial-allow-raw-effect`,
   `axial-note AXG014` becomes `axial-note task-surface`, and `[exemptions] AXG009` becomes `raw-concurrency`. The
   build names each one and its replacement; the full list is in the rules table in `docs/guardrails/01-guardrails.md`.
   `NoWarn` and `WarningsAsErrors` keep the number.
6. A human reviews the change with `axial policy review` and approves the lock once. The review reads old numbered
   allowances as their names, so renaming alone adds nothing to approve.

Coming from 0.14 or earlier, read the 0.15.0 notes first. A `Flow.fold` call with flow-returning handlers still
compiles in places and then never runs its handlers; change each one to `Flow.foldFlow`, or to `Flow.fold` with plain
handlers. Axial.Configuration and Axial.Hosting need Reified 0.13.0 or later, so raise a direct Reified reference to
match.
