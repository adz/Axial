# Axial 0.15.0

`Flow.fold` now takes plain handlers, and the folds that return flows take a `Flow` suffix. `Flow.exit` returns a
flow's whole outcome as an `Exit`. New combinators cover supervision, retry and timeouts, and new waits cover deferreds
and subscription refs. The test clock gains helpers, and `Axial.FileSystem` gains a rolling file log. The HTTP adapters
serve pages and forms as well as JSON APIs, with the same operations and request body limit on ASP.NET Core and
GenHTTP. Most packages now require only FSharp.Core 6.0.7, and the Fable-compatible ones install into Fable projects
with `dotnet add package`.

## Breaking changes and migration

| Was | Now |
| --- | --- |
| `Flow.fold onSuccess onFailure` with flow-returning handlers | `Flow.foldFlow onSuccess onFailure` |
| `Flow.fold (Flow.succeed << f) (Flow.succeed << g)` | `Flow.fold f g` |
| `Flow.foldCause` | `Flow.foldCauseFlow`, or `Flow.exit` and a match on the `Exit` |
| `Flow.foldCause (Exit.Success >> Flow.succeed) (Exit.Failure >> Flow.succeed)` | `Flow.exit` |
| Interrupting `Flow.awaitStartedTask` (or another `awaitStarted*`/`attemptStarted*`) waited for the task to finish | it stops waiting at once; the task keeps running |
| `EndpointOptions` built as a record literal | `{ EndpointOptions.Default with ... }`; the record gains `MaxRequestBodySize` |
| GenHTTP read JSON and form bodies of any size | bodies over 30,000,000 bytes end with a 413 problem response |
| ASP.NET Core `Request.form` on a body that is not a form failed with ASP.NET Core's exception | a 400 problem response |

Check every `Flow.fold` call. An old call with flow-returning handlers can still compile: `'next` becomes a flow, the
result is a flow of a flow, and the handlers' flows never run. The compiler rejects it only where the result's type is
fixed, such as `do!` or a type annotation; `let! _ =` and `Flow.ignore` accept it.

There is no pure `foldCause`. Use `Flow.exit` followed by a match, which keeps the cause explicit.

## Flow

Folds:

- `Flow.fold` takes `'value -> 'next` and `'error -> 'next` handlers.
- `Flow.foldFlow` and `Flow.foldCauseFlow` are the folds whose handlers return flows.
- `Flow.exit` succeeds with the flow's outcome as an `Exit`, the inverse of `Flow.ofExit`.
- `Flow.fold`, `Flow.foldFlow`, `Flow.exit`, `zip`, `map2`, `apply` and `map3` match the outcome once instead of going
  through several flow layers. On the .NET benchmarks (Fable was not measured), `foldFlow` and `map3` take about half
  the time, `foldFlow` also about half the allocation, and `fold`, `zip`, `map2` and `apply` take 10 to 30 percent less
  time.

Errors, retry and supervision:

- `Flow.orDie` turns a typed failure into a defect that holds the error, for failures the caller cannot handle.
- `Flow.retryForever` retries typed failures on an infinite schedule and never fails with a typed error.
- `Flow.superviseForever` restarts a long-running worker whenever it returns or dies with a defect, waiting a `Backoff`
  between restarts. A typed failure or an interruption stops it.
- `Flow.timeoutOption` returns `Some value` when the flow finishes in time and `None` when the timeout wins.
- `Exit.getOrThrow` returns a success value, rethrows a defect, and throws for a typed failure or interruption.

Construction and environment:

- `Flow.sync` runs a synchronous computation each time the flow runs.
- `Flow.envWithFlow` runs the flow the environment selects. `Flow.provide` runs a flow with a fixed environment.
- `Flow.fromUnitTask`, `Flow.attemptUnitTask`, `Flow.fromUnitValueTask` and `Flow.attemptUnitValueTask` take a
  `CancellationToken -> Task` or `CancellationToken -> ValueTask` with no result, such as a write, connect or copy,
  and succeed with `()`. Exceptions and cancellation behave as in `fromTask` and `attemptTask`.

## Coordination and logging

- `Deferred.poll` returns the outcome of a completed deferred, or `None` while it is pending.
- `SubscriptionRef.awaitWhere` waits until the value satisfies a predicate, and returns at once if it already does.
  `SubscriptionRef.awaitChange` waits until the value differs from its value when the wait started.
- `Queue.slidingNow` creates a sliding queue synchronously, as `Queue.droppingNow` does for a dropping queue.
- `LogSink.write` is public, for custom sinks that forward entries to another sink.
- `FileLog.sink` in `Axial.FileSystem` appends log entries to a file through `IFileSystem`. Past `MaxFileSizeBytes`
  it rolls the file into numbered archives (`app.log.1`, `app.log.2`, ...), keeping `MaxArchives` of them. With
  `MaxArchives = 0` it starts the file again.

## Testing

- `TestPlatform.createAt` creates a test platform whose manual clock starts at the given wall time.
- `TestClock.awaitSleepers` waits until a number of sleeps are registered, without spin-waiting.
- `TestClock.driveUntilDone` advances the manual clock until a fiber settles, and returns its exit.

## HTTP adapters

- Form and query field names follow Reified 0.13: dotted or bracketed names nest, numeric segments index lists, and
  an empty field is absent.
- `Request.parseForm` and `Request.parseQuery` return the schema's parse result instead of ending the endpoint, so a
  page can show its form again with each field's error and the values the user typed.
- `Response.html` returns a page or an htmx fragment. `Response.redirect` sends the browser on after a form post.
- `Response.withHeader` sets a header on any response. It replaces a value already set under that name, including one
  the response sets itself, such as `Content-Type` or a redirect's `Location`.
- `Axial.Hosting.GenHttp` gains `Request.form` for `application/x-www-form-urlencoded` bodies.
- `EndpointOptions.MaxRequestBodySize` sets the largest request body an endpoint accepts. A larger body ends
  `Request.json`, `Request.form` and `Request.parseForm` with a 413 problem response. `None` means 30,000,000 bytes on
  GenHTTP and the server's limit on ASP.NET Core, where Kestrel's default is also 30,000,000.
- On ASP.NET Core, a form past its `FormOptions` limits (a value over 4 MiB, too many values, or a multipart body over
  its limit) ends with the same 413 response instead of a 500.

## Packaging

- `Axial.Hosting`, `Axial.Hosting.AspNetCore`, `Axial.Hosting.GenHttp` and `Axial.Configuration` depend on Reified
  0.13.0. Core `Axial` and the other packages do not depend on Reified.
- Each library declares the lowest FSharp.Core it compiles against, instead of the SDK's. 0.14.1 required FSharp.Core
  10.1.403 from every consumer; most packages now require 6.0.7. `Axial.Configuration`, `Axial.Hosting`,
  `Axial.Hosting.AspNetCore`, `Axial.Hosting.GenHttp` and `Axial.ElmishFlows` require 8.0.100, the floor of their
  Reified and Elmish dependencies.
- `Axial`, `Axial.Console`, `Axial.FileSystem`, `Axial.Process`, `Axial.Configuration`, `Axial.Hosting.Node`,
  `Axial.Hosting.Browser` and `Axial.Telemetry.JavaScript` are packed as Fable libraries: each nupkg carries its F#
  sources under `fable/` and the `fable-javascript` tag. They need Fable 5.6.0 or later.

## Guardrails

- Within one build, projects share the protected-file list, the file digests and the policy check's result. A policy
  edit now runs `axial check --build` once per policy root in each MSBuild node instead of once per project.
- In a git work tree the protected-file list comes from `git ls-files`, the same list `axial check` protects, so
  ignored trees such as a NuGet cache inside the repository are no longer hashed.
- In a no-op build of an 18-project Windows solution, `AxialGuardrailsValidatePolicyCache` and
  `AxialGuardrailsWriteInputFingerprint` together took about 0.2 s per project, down from 1.5 to 10 s.
