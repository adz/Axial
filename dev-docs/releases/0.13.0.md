# Axial 0.13.0

Gaps found while building two Avalonia desktop applications on `Axial.ElmishFlows`: streaming results into `update`,
services owned by the runtime instead of a never-ending command, and handing work to an editor, file manager or
browser without a hand-written `System.Diagnostics.Process` call. `axial check --full` now names the F# projects it
fails because they are not checked at all.

Breaking: a custom `IProcess` must implement the new `Launch` member, `ProcessError` has a new `ShellOpenRejected`
case, and `ElmishRuntime.startService` returns a `Result`.

## Elmish

| Change | Behavior |
|---|---|
| Streaming command | `Cmd.OfFlowStream.latest key runtime stream onElement onError` runs a `FlowStream` and dispatches each element, in order, through `Post`. At most one element waits in `Post`: the stream pulls the next element only after `update` has seen the previous one, so a fast stream is slowed to the dispatcher's pace instead of flooding it, and nothing is dropped or merged; batch with `FlowStream.groupedWithin`. It shares keys with `Cmd.OfFlow.Latest`: a newer stream or command for the key interrupts the running stream and drops the element it left waiting in `Post`, as does stopping the runtime. A typed failure dispatches `onError` after the elements before it; completion dispatches nothing; defects go to `OnDefect`; an exception from `onElement` is reported to `OnDefect` and that element is skipped. `Cmd.OfFlow.Latest.cancel` stops a stream without a message. |
| Runtime-owned services (breaking signature) | `ElmishRuntime.startService name service runtime : Result<unit, ServiceStartError>` starts a `Flow<'env, Never, unit>` as a named fiber in the runtime's root scope, outside `init` and `update`. It returns `Error ServiceStartError.DuplicateName` while a service with that name is still running and `Error ServiceStartError.RuntimeStopping` once the runtime is stopping. `Stop`/`StopAndWait`/`Dispose` interrupt it and run its finalizers. A defect is reported to `OnDefect` under the service name, and so is a service that completes while the runtime is still running (`Error = None`), because a pipeline that ends early leaves the program waiting; interruption, and completion once the runtime is stopping, are silent. This replaces running a never-completing flow through `Cmd.OfFlow.perform` with an unreachable `onSuccess`. Unlike `Cmd.OfFlow.start`, which `update` runs and which is expected to finish, a service is started by the host, one per name. |
| `Cmd.OfFlow.attempt` fix | `Cmd.OfFlow.attempt` and `Cmd.OfFlow.Latest.attempt` dispatch nothing when the workflow succeeds. They previously passed an unreachable `onSuccess`, so every success was reported to `OnDefect` as a defect. |
| Results waiting at stop | A `Cmd.OfFlow.Latest` result or a stream's typed failure still waiting in `Post` when the runtime stops is dropped, as stream elements already were. Commands, streams, subscriptions and services share one reporting rule: defects, and a composite typed failure no callback could take, go to `OnDefect`; a pure interruption is silent. |
| Desktop recipe | A new guide, [Avalonia desktop application](/elmish/avalonia-desktop.html), compiles and runs its Axial parts (environment layer, search service, `update` with `Cmd.OfFlowStream.latest` and `Cmd.OfFlow.attempt`, an `ElmishRuntime.test` run, and the self-test) as documentation examples, and covers startup with `startLayer` in `OnFrameworkInitializationCompleted` (where `Post` can use the UI dispatcher directly, so no dispatcher is attached later), services, `Inbox` input with a debounce window that can change at runtime (the window is part of the subscription id), streaming results, timings carried in messages via `Clock.timed` so `update` stays pure, shutdown, and a `--self-test` path that returns `DotNetApp.exitCode`. `Axial.Hosting` remains for Generic Host, ASP.NET Core, systemd and console exit codes. |

## Process

| Change | Behavior |
|---|---|
| Detached launches | `Process.launch command` starts one command and returns once it has started; the child inherits the caller's standard handles, gets its own console window on Windows, is never awaited and keeps running after the flow. Arguments go to the executable as a list, never through a shell. `Process.shellOpen target` opens a path or URL with the default handler (`ShellExecute` on Windows, `open` on macOS, `xdg-open` elsewhere). Both return `Flow<'env, ProcessError, unit>` and never throw while the flow is built; a failure to start is `ProcessError.StartFailed`. |
| `shellOpen` safety (new `ProcessError` case) | Opening a target can run a program: `ShellExecute` runs `.exe`, `.bat` and `.cmd` files, `open` runs `.app` bundles and executable scripts, and `xdg-open` hands the target to the desktop's associated handler. Check paths and URLs from untrusted sources before opening them. An empty target, or one starting with `-` (read by openers as an option), fails with the new `ProcessError.ShellOpenRejected { Target; Reason }` and starts nothing; prefix a relative path with `./`. The guide no longer suggests `cmd.exe /c` for editors installed as scripts, which reinterprets `& \| ^ %` in a path; start the script's executable instead. |
| `IProcess.Launch` (breaking for custom implementations) | Launches go through a new `IProcess.Launch: ProcessLaunch -> Flow<unit, ProcessError, unit>` member, with `ProcessLaunch.Command` and `ProcessLaunch.ShellOpen` cases, so they are mockable. A custom `IProcess` must implement `Launch`; a host that cannot start programs returns `StartFailed`. `Process.test ()` records launches in `Launches`, succeeds by default, and takes a `LaunchHandler` to simulate failures; launches never call `RunHandler`. |

## Guardrails

| Change | Behavior |
|---|---|
| Unguarded projects | `axial check --full` still fails when an F# project in the solution is neither analyzed nor opted out with `<AxialGuardrailsEnabled>false</AxialGuardrailsEnabled>`, including a project that references `Axial.Guardrails` but whose props were not imported. The error now names each such project and says how to fix it (reference the package and keep its build assets, or opt out explicitly) instead of listing raw missing coverage records. C# projects are not listed. |
