# Axial 0.13.0

Gaps found while building two Avalonia desktop applications on `Axial.ElmishFlows`: streaming results into `update`,
services owned by the runtime instead of a never-ending command, and handing work to an editor, file manager or
browser without a hand-written `System.Diagnostics.Process` call. `axial check --full` now names F# projects that are
not checked at all.

## Elmish

| Change | Behavior |
|---|---|
| Streaming command | `Cmd.OfFlowStream.latest key runtime stream onElement onError` runs a `FlowStream` and dispatches each element, in order, through `Post`. It shares keys with `Cmd.OfFlow.Latest`: a newer stream or command for the key interrupts the running stream, and elements it posted that `update` has not yet seen are dropped, as are elements still waiting in `Post` when the runtime stops. A typed failure dispatches `onError` after the elements before it; completion dispatches nothing; defects go to `OnDefect`. `Cmd.OfFlow.Latest.cancel` stops a stream without a message. |
| Runtime-owned services | `ElmishRuntime.startService name service runtime` starts a `Flow<'env, Never, unit>` as a named fiber in the runtime's root scope, outside `init` and `update`. `Stop`/`StopAndWait`/`Dispose` interrupt it and run its finalizers; a defect is reported to `OnDefect` under the service name and interruption is silent. It returns `false` while a service with that name is still running or once the runtime is stopping. This replaces running a never-completing flow through `Cmd.OfFlow.perform` with an unreachable `onSuccess`. |
| Desktop recipe | A new guide, [Avalonia desktop application](/elmish/avalonia-desktop.html), covers startup with `startLayer` in `OnFrameworkInitializationCompleted` (where `Post` can use the UI dispatcher directly, so no dispatcher is attached later), services, `Inbox` input with a debounce window that can change at runtime (the window is part of the subscription id), streaming results, timings carried in messages via `Clock.timed` so `update` stays pure, shutdown, and a `--self-test` path that returns `DotNetApp.exitCode`. `Axial.Hosting` remains for Generic Host, ASP.NET Core, systemd and console exit codes. |

## Process

| Change | Behavior |
|---|---|
| Detached launches | `Process.launch command` starts one command and returns once it has started; the child inherits the caller's standard handles, is never awaited and keeps running after the flow. `Process.shellOpen target` opens a path or URL with the default handler (`ShellExecute` on Windows, `open` on macOS, `xdg-open` elsewhere). Both return `Flow<'env, ProcessError, unit>`; a failure to start is `ProcessError.StartFailed`. |
| `IProcess.Launch` (breaking for custom implementations) | Launches go through a new `IProcess.Launch: ProcessLaunch -> Flow<unit, ProcessError, unit>` member, with `ProcessLaunch.Command` and `ProcessLaunch.ShellOpen` cases, so they are mockable. A custom `IProcess` must implement `Launch`; a host that cannot start programs returns `StartFailed`. `Process.test ()` records launches in `Launches`, succeeds by default, and takes a `LaunchHandler` to simulate failures; launches never call `RunHandler`. |

## Guardrails

| Change | Behavior |
|---|---|
| Unguarded projects | `axial check --full` lists each F# project in the solution that neither references `Axial.Guardrails` nor opts out with `<AxialGuardrailsEnabled>false</AxialGuardrailsEnabled>`, once per check, in a `WARNING: ... do not reference Axial.Guardrails` message. The warning never changes the exit code. Such projects previously failed the check as missing coverage records. C# projects are not listed. |
